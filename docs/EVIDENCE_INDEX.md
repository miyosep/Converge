## Paired Kiln and Sepolia acceptance flows

| Flow              | Source artifact                                                                                     | What to inspect                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Baseline          | [group-acceptance-001-baseline.json](evidence/group-acceptance-001-baseline.json)                   | `policy`, `receipts`, `extractionAttempts`, `explanationAttempts`, `usage` |
| Lower budget      | [group-acceptance-001-lower-budget.json](evidence/group-acceptance-001-lower-budget.json)           | Same fields, plus `changedConditions`                                      |
| Merchant excluded | [group-acceptance-001-merchant-excluded.json](evidence/group-acceptance-001-merchant-excluded.json) | Same fields, plus `rejection`                                              |

All three use a synthetic restaurant catalog and six distinct keys/session identities operated by one test runner. They are historical v1 flows, not evidence of independent humans or current v2/xAPI/30% behavior. Provider call metadata includes real request IDs and failures/retries. Read-only rejection checks are not mined failed transactions.

[Submission verification report](evidence/submission-proof-verification.json) is generated by [verify-submission-proof.ts](../scripts/verify-submission-proof.ts). It rechecks each payment's successful receipt, destination, canonical block hash, decoded `PaymentExecuted` arguments and finalized height. It reads saved Kiln metadata, not the provider's live log service. The original lifecycle artifacts remain unchanged.

```sh
# .env contains only a Sepolia RPC_URL; no signing keys needed.
node --env-file=.env --import tsx scripts/verify-submission-proof.ts
```

The older `pnpm demo:groups-verify group-acceptance-001` performs broader lifecycle checks and updates original verification fields. Do not confuse it with the new non-mutating verifier.

## Reproduction and evidence hygiene

- Use Node/pnpm versions from package.json; Foundry/Anvil is needed for local contract rehearsals. Read each script's prerequisites before running it.
- Review [GROUP_ACCEPTANCE.md](GROUP_ACCEPTANCE.md), [LIVE_GROUP_PLANS.md](LIVE_GROUP_PLANS.md) and [LIVE_DEMO_BOOKING.md](LIVE_DEMO_BOOKING.md) for dated verification scopes.
- Preserve original records. Never fabricate provider IDs, transactions, independent-user participation or continuous runs by joining unrelated logs.
- Only already-published synthetic evidence is summarized by the submission verifier. Do not publish current private preferences, health data, sessions, private keys or authenticated RPC URLs.
- New current-flow recordings, if produced, need their own same-run provider logs and chain receipts. The current repository does not claim that all current flows already have that complete recording.
